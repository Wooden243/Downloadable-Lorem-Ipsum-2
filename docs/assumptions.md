# Assumptions and ambiguities — source vs implementation

1. **Programming language**: The provided lesson uses PHP code (`download.php`, `$_POST`, `header()`, `exit()`) even though a general language selector shows JavaScript in the page header. This project implements the illustrated PHP behavior directly.
2. **Previous restaurant project**: The earlier source bundle contained both a Node.js implementation and an equivalent PHP OOP class model. This extension uses and extends the **PHP class model** (`FileConvertible`, `User`, `Employee`, `Company`, `RestaurantLocation`, `RestaurantChain`) to avoid porting PHP server operations into JavaScript. The generated sample classes and random vocabulary are carried over, not copied from an external project.
3. **Composer and `vendor/autoload.php`**: The screenshot uses Composer autoloading, but no dependency package is specified or provided. `src/bootstrap.php` provides a lightweight local autoloader without vendor downloads. Model paths are namespaced instead of root-level `User.php`.
4. **Fallbacks vs strict validation**: The example initialises `$count = $_POST['count'] ?? 5;` and `$format = $_POST['format'] ?? 'html';`, then later instructs rejecting missing values. This implementation requires `count` and `format` in user POST forms, because that is consistent with the later explicit verification instruction. `dataset` defaults to `users` to preserve compatibility with submissions following the screenshot example.
5. **HTML behavior**: The example displays HTML rather than forcing a download. This project returns an inline HTML document; JSON/TXT/Markdown get fixed, safe attachment filenames.
6. **Restaurant fields**: The extension's exact schema is not provided. Additional form names (`chain_count`, `employee_count`, `location_count`, `salary_min`, `salary_max`, `postal_min`, `postal_max`) are our own and are validated in the server.
7. **Employee counts**: "チェーンが持つ従業員の数" is interpreted as employees **per chain**, not per location. Employees are distributed round-robin across the requested locations; branches may have zero employees if there are more branches than staff.
8. **Salary range**: The screenshot does not specify annual/monthly currency or bound limits. We use illustrative annual salaries in US dollars (integer amount 0..1,000,000) with inclusive bounds. The values are fictional.
9. **Postal code range**: The screenshot calls the range a ZIP code range; we model US-style 5-digit ZIP strings and accept numeric inclusive bounds 0..99999. The range is numeric for generation but zero-padded in the returned string to preserve leading zeros. ZIP/city combinations are not checked for geographic realism; these are synthetic records.
10. **Additional limit choices**: Max 10 chains, 100 employees/chain, 20 locations/chain. These bounded controls prevent very large downloads. The User count limit 1..100 **is specified** by the lesson, rather than invented.
11. **User data**: User IDs are sequential within each generated export and email addresses use `example.com`. Chain IDs are sequential from 1000; employee IDs are unique within each export. The system does not persist information between requests.
12. **Files**: The project does not create output files on disk; it streams an HTTP response. The browser handles the actual saving of attachments.
13. **Missing older lesson screenshot**: Only this (2) step and the earlier Restaurant Chain Mockup project bundle are supplied. No unsupported requirements from (1) are asserted. The user form and conversion methods are created here in a self-contained way.
14. **Auth / deployment**: No user login, real payroll processing or publicly hosted PHP deployment is required. The server is bound to 127.0.0.1 for development.
